1. NGUYÊN TẮC VẬN HÀNH CHÍNH
3 quy tắc vàng khi bấm nút
1) Mọi action phải có phản hồi tức thì (<100ms) — optimistic update UI trước, sync server sau. 2) Mọi action khả phá hủy (delete, reject) phải có Confirm Dialog hoặc Undo 5s. 3) Sau mỗi action, dữ liệu liên quan ở MỌI màn hình khác phải tự cập nhật (nếu đang mở).

4. TASK BOARD — UX CHI TIẾT (PHẦN TRỌNG TÂM)
4.1 Drag-Drop Card Giữa Cột (Kanban logic)
LUỒNG DRAG KHI THẢ VÀO CỘT MỚI:

Bước 1: User kéo card "KV Món Mới" từ [In Progress] sang [Ready for Review]
        → card theo con trỏ, cột đích highlight xanh

Bước 2: Thả card
        → OPTIMISTIC: card đã nằm ở cột mới NGAY LẬP TỨC
        → API call nền: PATCH /tasks/:id { status: 'ready_for_review' }

Bước 3a: API trả về OK
        → Không làm gì thêm (UI đã đúng)
        → Badge đếm cột +1/-1 cập nhật

Bước 3b: API FAIL (mất mạng / lỗi validation)
        → Card BAY VỀ cột cũ với animation ngược
        → Toast: "Không thể chuyển task. Đã hoàn tác."
        
EDGE CASES PHẢI XỬ LÝ:
├── Thả "Approved" card về "In Progress"? 
│   → HIỂN THỊ CONFIRM: "Task đã duyệt. Chuyển về In Progress
│     sẽ gửi notification lại cho designer. Tiếp tục?" [OK] [Hủy]
├── Thả card vào cột bị khóa WIP limit (>5 cards)
│   → Cột rung đỏ + toast: "Cột đã đạt giới hạn 5. 
│     Hoàn thành task trước khi thêm mới."
└── Drag trong mobile → KHÔNG dùng drag, thay bằng:
    card menu (⋯) → "Move to..." → chọn cột từ bottom sheet
State machine chuyển đổi hợp lệ:
const allowedTransitions = {
  'requested':    ['in_progress', 'cancelled'],
  'in_progress':  ['ready_for_review', 'requested', 'cancelled'],
  'ready_for_review': ['approved', 'revision_needed', 'in_progress'],
  'revision_needed': ['in_progress'],
  'approved':     ['delivered'],           // ← khóa, không quay đầu
  'delivered':    []                        // ← terminal state
};

// Nếu drop vào cột không hợp lệ → card弹 về + toast giải thích
// "Không thể chuyển từ Approved về In Progress trực tiếp"

4.3 Approve Flow — End-to-End
BẤM [✓ APPROVE]:

Bước 1: UI khóa nút ngay (disabled, spinner)
        API: PATCH /tasks/:id { status: 'approved' }

Bước 2: API OK → trên panel:
        ├── Status badge flip sang xanh "✅ Approved" (flip animation)
        ├── Nút [Approve]/[Reject] ẩn đi, thay bằng [Mark Delivered] + [Undo 5s]
        ├── Notification đẩy đến designer (badge +1, push mobile nếu bật)
        └── Card ở board lùi upstream cũng flip trạng thái (sync!)

Bước 3: User nhận ra nhầm nút → bấm [Undo 5s]
        → API revert status về 'ready_for_review'
        → TẤT CẨU UI sync ngược lại (panel + board + notification rút)
        → Sau 5s nếu không bấm → Undo biến mất, action thành thật
        
ĐÂY LÀ LÝ DO "OPERATION" KHÁC "UI":
- UI chỉ vẽ nút Approve đẹp
- Operation phải lo: race conditions (2 người approve cùng lúc?
  → server check version, người sau nhận "Task vừa được duyệt bởi Admin"),
  undo window, cross-screen sync, notification routing

7. CÁC LUỒNG VẬN HÀNH ĐẦY ĐỦ (USER JOURNEYS)
Journey 1: Stakeholder gửi request → nhận成品
[Marketing nhân viên]
  1. Bấm [+ New Request] trên All Tasks
  2. Điền form → Attach brief PDF → Submit
     → UI: task xuất hiện cuối cột "Requested" NGAY
     → Toast: "Đã gửi. Được gán cho Wendy (theo cân bằng workload)"

[Designer Wendy]
  3. Nhận notification "Bạn được giao task mới" → click
     → Landing thẳng vào task detail
  4. Bấm [Start] → status → in_progress, timer start
  5. Làm xong → bấm [Submit version] → upload file PSD
     → progress bar → preview tự generate → status → ready_for_review

[Reviewer Luna]
  6. Notification "Wendy submitted v1 #TK15" → click → detail
  7. Xem preview → bấm annotation mode → ghim 3 chú thích lên hình
     → mỗi pin gắn comment cụ thể
  8. Bấm [Request Revision] → status → revision_needed
     → designer nhận notification có kèm 3 comments

[Wendy]
  9. Notification → click → thấy 3 pins trên v1
     → sửa đúng chỗ được chỉ → submit v2 → lặp lại 6-8

[Luna] 10. v2 đạt → [✓ Approve] → status approved
[Marketing] 11. Notification "Design của bạn đã hoàn thành 🎉"
              → click → download final files

TOÀN BỘ JOURNEY: 0 email, 0 screenshot qua Zalo, 0 "anh xem file em
gửi sáng nay chưa?" — mọi thứ nằm trong app và MỌI bước bấm được
Journey 2: Manager cứu task muộn
Manager mở Home buổi sáng 8h:
  → KPI "3 overdue" đỏ → click
  → Land: All Tasks filter overdue, sort muộn nhất trước
  → Mở task "KV Banner" (muộn 5 ngày, v3/5 revision)
  
  Áp lực kép → quyết định:
  
  NẾU LÝ DO MUỘN LÀ REVIEWER CHẬM:
  → Timeline panel cho thấy "v3 submitted Oct 1, review pending 2 ngày"
  → Thay vì mắng designer → nhắn/chuyển giao reviewer
  
  NẾU DESIGNER QUÁ TẢI:
  → Click assignee Wendy → workload pop-up "92% capacity"
  → Click [Reassign] → dropdown chỉ gợi ý user capacity thấp
  → Chọn Lisa (20%) → task chuyển, cả 2 nhận notification
  
  NẾU KHÔNG THỂ CỨU:
  → Menu (⋯) → [Extend deadline] → date mới + reason
  → hệ thống ghi deadline change vào timeline (audit trail)
Journey 3: Loop bảo vệ chất lượng
Auto rules chạy nền (cron mỗi giờ):

Rule 1: Task 'ready_for_review' > 48h chưa ai duyệt
        → Nudge reviewer: "Bạn đang chặn #TK15 (48h)"
        → Sau 72h → escalate lên manager của reviewer

Rule 2: Revision count = 4 (gần max 5)
        → Warning banner trên task detail:
          "Nhiều vòng sửa — cân nhắc hop kickoff để đồng bộ brief"
        → Không chặn, chỉ gợi ý

Rule 3: Due trong 24h nhưng chưa có version nào submit
        → Alert designer + team lead

Rule 4: Weekend/holiday → task due ngày đó
        → Auto suggest: "Dời deadline sang thứ 2?" [OK]

Ai thấy nút gì:

[+ New Request]        → mọi role (trừ Viewer)
[✓ Approve / ✗ Reject] → chỉ reviewer + manager của project
[Assign/Reassign]     → manager + trở lên
[Delete task]         → manager + trở lên (author cũng được, 
                         nếu task status ∈ [requested, draft])
[Extend deadline]     → manager + reviewer
[Submit version]      → chỉ assignee chính
[Edit brief]          → author + manager (khi chưa có version nào)

10. DEFINITION OF "BẤM VÔ DÙNG ĐƯỢC" — TEST SCRIPT
QA chạy checklist này trên MỖI button trước khi bàn giao:
□ Bấm nút → có phản hồi < 100ms (dù là chỉ disabled + spinner)
□ API fail → toast lỗi + UI rollback đúng trạng thái cũ
□ Double-click nhanh 2 lần → KHÔNG tạo 2 task / gửi 2 lần
□ Bấm nút xong → quay lại màn hình trước → data vẫn đúng (persisted)
□ Bấm action ở tab A → mở tab B song song → B tự refresh data
□ Refresh trang giữa chừng → không mất filter/position
□ Network chậm 3G (throttle) → vẫn dùng được, không đơ
□ Bấm trên mobile → responsive hit-area ≥ 44x44px
□ Keyboard-only tab → đi hết mọi nút, Enter hoạt động
□ Back button browser → quay đúng trang trước đó (không về / luôn)
□ Nút ngoài quyền → không render
□ Undo hoạt động trong cửa sổ thời gian cho phép
Ranh giới UI vs UXcritical
UI hoàn thành khi mọi màn hình vẽ đẹp. UX hoàn thành khi: user mới không cần hướng dẫn, user cũ không cần chờ, và user bấm sai thì luôn có đường về. Checklist mục 10 chính là cổng nghiệm thu giữa UI → UX.
